# 处理方法与实际进展

## 目标和筛选规则

底图库只收集能看清产品形态的照片。纯包装盒、封闭包装袋且看不到产品的照片不入库。带盒但产品外露、透明袋中可以辨认产品、同款不同角度应保留。不能凭“包装列”直接删除，模糊或不确定的图片先保留原图，避免漏产品。

## 实际走过的路径

1. 在线原表受区域保护限制；创建副本被明确禁止，Excel 导出未获得文件。
2. 早期复制文件只有 192 个真实媒体文件，很多位置是空图片对象；因此旧批次不是完整来源。
3. 用户将图片复制到新文件并保存后，桌面工作簿增长至 411092924 字节；重新读取文件，发现 2442 个媒体文件和 2648 个有效图片引用。
4. 用 ZIP CRC 检查容器完整性；解析 workbook、sheet、drawing 的关系链；每个图片位置记录工作表和单元格，再把 xl/media 中的原始字节写出。
5. 计算 SHA-256、图片宽高和格式，并验证图片可解码。重复引用只重复登记来源，不重复制造一份图片文件。
6. 为了不漏图，本轮提取保留全部原图；未把机器猜测当成已完成的人工筛选或分类。

## 图片检索方案与边界

网站分“保存底图”和“上传图片找同款”两个入口，支持选择、拖放、粘贴及图片地址。底图保存在服务端；待对比图不应自动进入底图库。误入的 WPS 测试图已移入可恢复区域，避免测试时检索到自己。

已实现基于 Transformers.js / CLIP 的图片特征检索，先按名称或类目缩小候选范围，若无可靠候选，再检索全部底图。相似度是视觉参考，不能当成已确认同款。旧模型目录基于 Xenova/clip-vit-base-patch32；以源码中的模型标识和 package/lock 文件为复现依据。

早期只有 182 张图片完成过特征写回，零样本自动命名准确率不足；不能用该结果替代本次 2442 张的筛选。history/save_products.py 的图片编号排除规则仅针对旧的 192 张，严禁套用到新工作簿的相同编号。

## 产品相似度与双模型对照（2026-11-24）

用户明确判据：表格「一行 = 同一个产品的不同角度」；底图是实拍、对比图是展示图，视觉 cosine 只能辅助；文本标签错误率高（17 个被 CLIP 标成「切割片套装」的组里只有第473行是真切割片），不能作为主判据。因此排序改为按来源行分组，用组内最高单张×0.6 + 强命中(≥0.65)比例×0.25 + 组内平均×0.15 得到产品分数。

模型对照没有只看单个案例：用全部 761 组中 743 个可留一验证组生成 1486 次查询，排除查询图本身，比较 CLIP、DINOv2-small 和两者融合。结果（reports/model-comparison.json）：CLIP 召回@1 41.59%/@5 63.32%；DINOv2-small 44.15%/64.00%；按每次查询组内 z-score 等权融合 50.07%/69.92%。单看 `1.webp` 三者都把第473行排第一，但融合分数领先第二名 3.47 个标准差，区分度更稳。站点据此接入双模型，DINOv2 q8 模型随站点本地发布；模型加载失败自动退回 CLIP 单模型，不会让页面不可用。

定名不是只看图猜：分组联系表切成放大图块逐格目检，761 组全部定名并回写站点元数据，105 组因图片信息不足保守标注「待复核」；重点组做公开来源交叉核对，证据链接在 reports/external-sources.json。无法从图片证明的品牌、型号、材质一律不写。期间发现并修正了早期 5 条把「来源行号」误当 groups.json 数组下标的标签（1.webp 真同款实际是索引 471、来源行 473），避免把品名贴到相邻产品上。

重建后本地真机验证：Chrome 通过 CDP 上传 `1.webp`，页面显示「CLIP + DINOv2 双模型融合」，首位卡片为「彩色花纹切割片/打磨片(4片装)」、产品匹配度 5.340（双模型）/视觉 0.703/3 个角度，第二位 3.847；控制台 0 错误。此前 7 个站点回归脚本全部通过；`verify-model.mjs` 与 `verify-real-library.mjs` 的旧 182 图路径已修到当前 2430 图库。
